# 限额改动

控制一次授权允许产生的总改动，降低用户 review 的负担。预算是上限，不是必须用满的指标；本技能不授予额外任务、文件、角色或外部操作权限。

## 授权与计数

- 修改前明确目标、允许扫描和修改的范围、行数上限 N，以及可观察的完成条件。用户已明确的内容直接采用；缺少预算时先询问，未确认前只读调查。N 为非负整数；N=0 时只读报告。
- 默认以本次授权开始时的文件内容为基线，计算最终待 review 差异的新增行数加删除行数；替换一行计 2 行。代码、测试、配置、文档、注释和空行跨文件合计，新文件全部行计入，已有用户改动不计入且不得覆盖。用户明确指定其他口径时，先记录口径再执行。
- 同一授权内的返修、审查反馈和续做均对原基线计数；内部试改不按编辑次数累加。恢复本次授权内自己的试改后，按最终 diff 重新核算；不得撤回用户既有改动或其他授权的成果来抵扣本次额度。用户 review 通过、提交、换文件、换模块、分批交付或新一轮对话均不自动重置预算。
- 用户要追加或重置额度时，明确这是将原总额提高到多少，还是以当前已 review 状态为新基线另行授权；“继续”本身不代表增加额度。沿用原授权时，原任务须尚未结束，且拟议修改后相对原基线的总差异不得超过 N；满额时仍可进行最终差异不增加的必要返修。
- 二进制、不可可靠逐行比较的文件和工具自动生成的额外改动不能默认算作零行；先报告影响并商定独立计量方式或排除修改。禁止压缩语句、合并多行、批量格式化、移动文件或隐藏生成物来规避计数。

## 选择最小业务单元

1. 读取项目规则、本地规范、工作树状态及相关代码，记录分支/提交、授权时点、已有改动和计数基线。无 Git 时记录文件快照或可复核的内容摘要；基线无法可靠取得时停止修改。扫描范围不明且可能明显扩大任务时先询问，不把局部扫描称为全仓扫描。
2. 在授权范围内列出有证据的候选项：位置、触发条件或需求依据、影响、优先级、预计行数和验证方式。缺陷采用项目分级，无项目分级时按安全/数据损坏或核心不可用、重要功能错误、局部功能错误、一般改进排序；同级再比较影响范围、可达性和证据充分度。开发按已确认需求优先级，优化按测量证据与收益，重构按已确认结构目标选择，不把推测当成缺陷。
3. 一个最小业务单元应完成一个可观察结果，包含必需的调用方、契约、错误路径、配置和验证资产；允许跨文件或模块。不能留下已知失效路径、破坏兼容性，或将修复必要部分推到未获授权的下一次改动。
4. 按优先级选择预算内能够完整交付的一个单元，不因剩余额度夹带无关改动。最高优先级项超额时，先报告证据、完整修复所需范围及行数估算；用户已授权自主选择时，可选择下一项能完整完成的候选并说明跳过理由。若高优先级项会使其他改动不安全或无效，停止，不绕过它。
5. 无候选能完整落入预算、需求存在关键歧义，或必要测试/迁移等配套工作超额时，保持只读并报告最小完整方案、预计行数及估算不确定性，请用户调整范围或额度。不先交付半个单元，也不自行提高额度。

## 实施、验证与停止

- 实施前估算完整 diff，预留必要验证与返修空间。每次写入前读取最新文件，在内存或临时工作区预览拟应用的差异并核算总量；预计超过 N 时不应用。临时文件不成为绕过最终交付计数的旁路。
- 写入后核对实际 diff 和文件列表。Git 可用 `git diff --numstat` 与逐文件 diff 交叉检查，但必须单独纳入未跟踪文件、已暂存内容以及混有用户改动的文件；不能直接将整个工作树相对 HEAD 的差异认作本次授权消耗。
- 检测到并发改动或基线漂移时停止写入，重新核对归属；无法区分时请用户协调，不自行覆盖或重新设定基线。若实际意外超额，立即报告事实、原因及当前差异，不继续扩改；恢复也须遵守项目授权，不能擅自删除文件或回滚用户内容。
- 运行与行为、边界和失败路径相称的现有测试、构建或静态检查；必要时补充验证资产，全部纳入预算。验证工具若可能生成或修改文件，先检查副作用并纳入预估；无法限制时改用只读验证或报告阻塞。失败后的修正仍对原基线重新核算，拟议最终总量不得超过 N；无法完成就报告部分状态及恢复方案，不宣称交付成功。
- 该技能是额度约束，不替代角色职责。在本项目中，实现由 [dev](../dev/SKILL.md) 负责；代码修改先经 [cr](../cr/SKILL.md) 再进入 [qa](../qa/SKILL.md)，QA 通过后由编排者核验完成门禁。缺陷登记、优化项前置条件、独立代理及任务视图要求沿用原流程；不以小改动绕过，也不为单独使用本技能默认启动 SC。所需角色或工具不可用时报告门禁未完成，不模拟通过。
- 完成选定单元或遇到阻塞即停止本次修改，等待用户 review；即使有余额，也不自行选择下一单元。review 反馈属于原目标返修时沿用原基线和总额，已结束任务的新工作须重新授权。提交、同步、发布和生产操作分别遵循项目授权，不由额度授权推定允许。

## 交付证据

提供简短报告，足够让用户 review 与接续：

- 授权目标、范围、N、计数口径、基线标识、当前版本/工作树状态、验证环境与观察时间。
- 选定单元、可观察结果、选择依据，以及跳过的更高优先级项及原因；证据使用实际文件路径与行号、需求或已有测量记录。
- 精确文件列表、各文件新增/删除数、总消耗与剩余额度，以及可审查 diff。已有用户改动与本次差异明确区分；展示前脱敏，不输出密钥或受限数据。
- 已运行命令、结果、覆盖与未验证范围，CR/QA 等门禁的实际状态；代码已写入、开发验证通过和正式验收通过分别表述。
- 状态为“单元完成，等待 review”“预算不足，未修改”或“部分修改/验证阻塞”，附未解决风险、恢复条件及需要用户决定的最小事项。估算不是实际行数，静态推断不是运行验证，未完成门禁不能宣称整体完成。

例如，用户授权“最多改 20 行，自行扫描并按缺陷级别选择”时：替换 7 行并新增 4 行测试，共 18 行，可交付一个完整修复；若完整修复需替换 11 行，仅代码就需 22 行，必须报告超额，不能拆成两次 11 行修改后继续执行。
