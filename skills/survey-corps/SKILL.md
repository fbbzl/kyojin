# 调查兵团

调查兵团用于跨角色工程协作：用最少的角色完成任务，并让结论能追溯到当前范围、版本、环境和证据。它协调 `req`、`dev`、`cr`、`qa`，不替代专业判断；代码同步、发布预检、生产发布及运行观察由用户或授权方负责。

## 启动别名

用户明确说“启动 `sc`”“运行 `sc`”或等价表达时，无论任务看起来需要几个角色，都启动调查兵团，并继续遵守本技能的最小角色链、subagent-only 和交接约束。`sc` 只是调查兵团的简称，不代表普通会话、独立任务或另一套工作流。

显式启动 `sc` 后，编排者必须立即为**当前任务**调用 `show_sc_task_view(snapshot)`。该工具由 `survey-corps-task-view` MCP Apps server 提供，将 `structuredContent.snapshot` 传给 `ui://survey-corps/task-view` MCP App，并由宿主在内嵌 iframe 中渲染 HTML/CSS/JavaScript。`req`、`dev`、`cr`、`qa` 不是独立总视图入口，而是该总视图内可展开的成员子视图。

- 任务视图只有一条渲染路径：`show_sc_task_view(snapshot) -> ui://survey-corps/task-view -> 宿主内嵌 iframe`。禁止创建、复制、打开或展示本地 HTML 可视化产物，禁止文本、Markdown、Mermaid 或其他替代任务视图。
- 角色卡严格按 `work_unit.roles` 中有效角色首次出现的原序自上而下展示，不按状态或固定角色表重排；不在角色链后渲染 SC 回流门禁。每个角色是可折叠任务卡，角色框展示状态、通过后的耗时和逐行排列的子技能调用名称，并随内容自然增高，详情仅展示摘要、必要证据和风险；状态机参考集、独立元数据面板、console 和 session log 不进入视图。
- 渐进展示只自动展开一个当前活动角色，其余角色保持折叠；用户手动展开任一角色时也必须关闭其他角色，任何时刻最多显示一个详情区。角色严格串行执行，同时最多一个角色显式 `status=running`；QA 常规运行要求当前选中的 CR 显式 `status=passed`，独立测试资产限定返修按下文交接规则执行。显式未完成的前序角色不得跳过，旧快照缺失历史状态仍兼容。服务端对每个含 `work_unit.roles` 的快照先校验任务状态与角色状态一致性；首次有效快照建立基线，后续只接受合法阶段跳转，同一 `view_id` 的工作单元和角色顺序不可变。矛盾更新在缓存和计时前拒绝，保留最近有效快照；服务重启后重新建立基线。直接渲染此类旧快照时不高亮、自动展开或播放交接动效，不改写角色原始状态。没有显式 `running` 时，不高亮或自动展开任何角色；任务阶段不能推断角色执行。显式全局停止状态（与耗时停止规则一致）优先抑制活动提示和自动展开，即使角色仍残留活动状态。同一 `view_id` 且活动角色未变化时，保留有效的手动展开或全部折叠选择；切换任务或已展开角色被移除时，重新跟随当前活动角色。同任务刷新保留仍存在且可见的角色标题及预览正文焦点；不跨任务恢复焦点或抢占视图外焦点。
- `show_sc_task_view` 工具缺失、MCP App 资源无法加载或工具调用失败时，立即将当前工作单元标记为 `blocked`，停止启动角色或继续交接。阻断报告必须说明实际错误，恢复条件为安装并启用 `survey-corps-task-view` 插件、启用 MCP Apps，必要时重启宿主客户端并在新会话中确认该 tool 可用后重试。不得以任何降级视图绕过阻断。
- 每次角色启动、交接、状态变化、风险或证据变化，以及真实当前操作文件切换时，必须再次调用同一 `show_sc_task_view` tool 更新快照。视图仅随这些明确的编排动作刷新，不声明自动事件订阅、后台轮询或平台原生实时同步。
- 每个工作单元的 `work_unit.roles` 只列本轮实际执行的角色，不沿用历史工作单元的角色链，也不默认填写全部角色。已登记 Bug 的默认链路为 `dev -> cr -> qa`；只有仍存在会改变方案或验收的需求歧义、且本轮确实需要 REQ 收敛时才前置 `req`。清晰的功能请求直接从 `dev` 开始。参与顺序由编排者按当前场景确定，例如常规 `dev -> cr -> qa`、优化 `cr -> dev -> qa`；不忽略已确认的参与列表重新推断。复审更新原角色卡，不复制角色。
- 启动所选角色前，先提交包含该角色且其 `role_details.<role>.status=running` 的快照，并确认工具调用成功，再启动对应 subagent。首次快照若在角色完成后才发送，服务端无法回算该角色此前的耗时；不得用任务总耗时推算角色耗时。
- MCP App 展示不是权威记录，也不能改变状态机、角色交接、完成门禁或 subagent-only 约束。权威记录仍是当前任务中的工作单元、交接和角色结论。

### 快照更新与输出

按 `view_id` 缓存成功接收的 `structuredContent.snapshot`；更新时复制缓存、只改变化字段，仍发送完整快照。同一次编排动作的字段合并更新；不跨角色启动、交接或真实文件切换合并。当前已展示同一视图且 JSON 内容未变时跳过调用，不输出确认；不为计时或装饰重复刷新。成功且返回 ID 匹配才替换缓存；失败报告实际错误、保留旧值并停止交接。缓存丢失按权威记录重建；`{}` 仅恢复服务端最近快照，须核对 ID，不能代替更新。只输出真实 `result.content` 文本，不输出或顶层返回整份 result/snapshot；不重复读取或输出 HTML、CSS、JS 及历史快照。

当前 `functions.exec` 每会话只定义一次 helper，所有更新串行等待；`store` 保存静态源码字符串，不保存函数。工具名以当前声明为准；首次、显式重新展示或服务端重启后，把完整权威快照作为第三参数强制发送，后续仅传变化。摘要保留结论、证据保留定位，不把日志或源码复制进快照，也不裁剪上报历史。

```javascript
store("sc-update", `async (viewId, change, initial) => {
const key = "sc-snapshot:" + viewId, saved = initial ?? load(key);
if (!saved || saved.view_id !== viewId) throw new Error("缺少当前任务缓存；按权威记录重建完整快照。");
const before = JSON.stringify(saved), snapshot = JSON.parse(before);
change(snapshot);
if (initial == null && load("sc-current-view") === viewId && JSON.stringify(snapshot) === before) return;
store("sc-current-view", null);
const result = await tools.mcp__survey_corps_task_view__show_sc_task_view({ snapshot });
for (const item of result.content ?? []) if (item.type === "text") text(item.text);
if (result.isError) throw new Error("视图更新失败，停止交接；实际错误见工具返回。");
const accepted = result.structuredContent?.snapshot;
if (accepted?.view_id !== viewId) throw new Error("快照 ID 不匹配；停止交接。");
store(key, accepted);
store("sc-current-view", viewId);
}`);
// 后续调用只需这两行；eval 的输入仅限本会话定义的静态 helper。
const update = eval(load("sc-update"));
await update("sc-task-view:<work_unit_id>", snapshot => { snapshot.role_details.dev.summary = "本轮实际变化"; });
```

### 任务视图数据契约

含 `work_unit` 的业务快照必须带已知 `state` 和 `roles`；首次校验阶段与角色一致性，后续同时校验阶段、角色跳转及不变的工作单元/角色顺序。暂停、等待、全局阻断或结束时须在同一快照停止角色，不再接受残留 `running`；首次恢复暂停/补材料快照须给出 `resume_state`，已有会话按保存的来源阶段恢复。`needs_revalidation` 必须声明最早失效阶段，完成后不能直接重新执行；基线变化也须进入复验或重新 CR。CR 阻断可先展示而未启动返修；恢复复审前必须已观察到获授权的限定返修。无工作单元的旧纯视图仍兼容，但已绑定任务仅允许纯暂停/等待控制，推进和结束必须发送完整快照。非法更新不会自动纠正状态，也不改变缓存、阶段记录或计时。

当前角色可上报可选 `role_details.<role>.file_activity={previous?,current,next?}`，值均为真实系统绝对路径（盘符根路径或 POSIX 根路径），旧仓库相对路径兼容；拒绝 UNC、URL、控制字符及 `..` 段，不由视图拼接工作区路径；编排者可提供明确的 `work_unit.project_root` 系统绝对根目录；三槽仅将其严格后代文件派生为项目级显示路径，title 保留真实完整路径。盘符路径大小写不敏感且兼容两种分隔符，POSIX 大小写敏感；未知或非法根、根外及旧相对路径保持原安全显示，不猜测项目根、不改写身份或因根变化补播滚动；REQ/DEV/CR/QA 在实际文件操作开始前或切换时通过协作消息报告给唯一快照写者，完成后清除 current，同文件连续操作不重复上报，next 仅填写已确定的下一文件。编排者收到切换立即刷新；不扫描 mtime、不解析摘要、不轮询或宣称自动捕获。右侧详情顶部文件条只展示当前预览且唯一合法活动角色的上报：上一文件露下半行、当前完整一行、明确下一文件露上半行，长路径可横向滚动，无前后项留白；窄屏在活动角色内联详情顶部复用同源文件条，桌面正文副本移除该内联条；无效路径、停止或预览其他角色时清空但保留固定高度。同任务同活动角色有效 current 变更向上滚动一次 220ms，初载、同值刷新、换任务/角色不补播，减少动态偏好下静态。

右上总状态使用 33.8px 字号、固定 31.2px 行高。角色状态精确为 `pending` 或 `needs_user_confirm` 时，角色名旁改用装饰性 ⌛，沿用所属角色周期，前 70% 静止后翻转；等待动效不依赖角色运行高亮，任务进行中的非活动待开始角色也可播放，仅提示等待、不表示执行或改变门禁。总状态为 `needs_user_confirm` 时仍播放，`paused`、`waiting`、`blocked`、取消或结束及减少动态偏好下静止；这一停止规则仅指沙漏，不限制下述阻断角色提示。

角色精确为 `passed` 时展示 🎉 并持续间歇庆祝；历史加载、同值刷新和任务完成后继续，退出 `passed` 或移除角色停止。全部角色表情按 REQ/DEV/CR/QA 使用 2.4/2.9/3.4/3.9 秒周期及不同负延迟，伪元素沿用角色时序，不影响卡片、状态、连线和外框周期。庆祝仅用两个固定 CSS 伪元素，不占布局，不新增字段、计时器、canvas、粒子系统或依赖；减少动态下静止且无彩带。喷射轨迹等视觉参数见 [MCP App README](mcp-app/README.md#git-信息与角色表情)。

角色精确为 `blocked` 时，默认使用 👻 轻微上下漂浮并渐伸、收回固定 CSS 舌头；只有 CR 或 QA 且 `blocker_type` 精确为 `bug` 时，改用 🐞 小幅左右爬动并间歇停顿。两者复用所属角色周期，在总状态为阻断时仍提示，真正暂停、取消、结束或减少动态偏好下静止。`blocker_type=bug` 仅控制装饰，不改变状态或门禁；CR 的 `test_assets` 同时用于下述限定返修门禁，表情仍为普通阻断。不根据摘要关键词推断。

可选 `work_unit.git` 在整个视图最左上角、项目 MCP 上方仅展示仓库名和分支名，以“ · ”连接，不加 Git 前缀；旧 `commit`、`dirty` 兼容保留但不展示。它与右侧总状态共用同一顶栏；宽窄屏均保持左右布局，仓库名和分支名均无有效值时隐藏该内容，状态仍靠右，长文本在左列自然换行，不挤压或覆盖状态。仅在任务开始或交接等明确刷新时采集，不增加 Git 后台读取或轮询。角色精确为 `running` 时，角色名旁显示装饰性 🔥，仅复用合法活动角色判定播放所属角色周期的燃烧动效：火焰轻微非均匀摆动，固定 CSS 火舌变化、火星上升；任务停止、非法活动快照和减少动态偏好下静止，不改变状态标签或交互，也不采集或推测 token 用量。

左侧角色链圆角虚线框随内容增高，无角色时隐藏；仅合法活动且任务未结束时沿框流动，否则及减少动态下静止。不包含详情、不拦截交互、不改变布局、不新增轮询或 JS 帧循环；线宽和周期见 [MCP App README](mcp-app/README.md#git-信息与角色表情)。

“参与角色”按同一有效去重原序显示为紧凑的 2px 圆角标签，相邻名称以长 22px、粗 2px 的水平箭杆连接，箭尾、箭尖贴住两侧标签边框，亮条与箭杆共用中心线。窄屏将角色链放在字段名下一整行并跨满元数据两列，保留标签字号、内距和箭头长度，其他字段位置不变。箭头亮条与角色链虚线框共用合法运行判定，箭头保持 1.8 秒周期，外框为 1.2 秒，仅为流程装饰，不表示真实交接；停止、结束、非法活动和减少动态偏好下静止，不新增状态或数据字段。

MCP App 资源 `mcp-app/assets/sc-task-view.html` 的渲染函数接收根元素、快照和可选调试选项：`window.renderSurveyCorpsTaskView(root, snapshot, options)`。正式调用不传第三参数。只有 `options.debug === true` 才显示并启用“播放动画”；`snapshot.debug` 和字符串 `"true"` 均不能开启调试。默认合法活动角色的边框显示低幅度呼吸动画，卡片内部复用同一 `sc-running-pulse`（1.8 秒、ease-in-out），以对应角色色的 3% 至 8% 混入 `--panel-active` 轻微明暗变化，明显弱于边框且不改变文字透明度；符合下述权威交接契约时，连接线额外播放一次流光，接收卡片随后短暂提亮。其余视图和状态更新保持静止；元数据、详情正文和耗时缺失时留白，不自动生成“未提供”占位；详情标题与有效内容保留，空详情正文保留一行高度，不填入占位文本或假数据，空列表项不生成项目符号，0 和 false 按有效内容展示，用户明确输入的字面“未提供”仍保留。“状态未提供”“未知状态”等语义提示维持原规则，不得由视图猜测完成、通过或风险关闭。

```yaml
work_unit:
  work_unit_id:
  project_name:          # 可选；当前会话所属项目名称，UI 不展示，不得猜测
  project_root:          # 可选；明确系统绝对根目录，仅用于三槽显示项目级路径，title 保留原路径
  project_mcps: []       # 可选；当前项目已生效的 MCP 名称，由编排者明确提供；UI 左上角折叠展示，不读取本机配置
  git:                  # 可选；编排者在开始或交接刷新时采集，不轮询；最左上角文本展示
    repository:         # 可选；仓库短名称字符串，不传本机路径或远端 URL
    branch:             # 可选；当前分支字符串，游离 HEAD 时省略
    commit:             # 可选；旧字段兼容保留，UI 不展示
    dirty:              # 可选；旧字段兼容保留，UI 不展示
  target:
  task_type:             # 可选；当前任务类型文本
  roles: []
  role_selection_reason: # 可选；编排者选择参与角色的原因
  scope: []              # 可选；文本或列表，保留在快照中但不在视图展示
  summary:               # 可选；任务总结的结果文本，与已验证、注意事项按有值分组展示
  reference_version:
  environment:
  verified_scope: []
  unverified_scope: []
  acceptance: []
  risks: []
  evidence: []
  next_action:
  metrics:                # 服务端自动填充 elapsed_ms；首次可提供实测基线，UI 展示任务累计耗时
view_id:                 # 必填；稳定逻辑 ID，格式为 sc-task-view:<work_unit_id>，UI 不展示

role_details:            # 可选，以 req/dev/cr/qa 为键
  req:
    status:              # 可选；仅 pending/running/passed/blocked/needs_user_confirm；交接记录不能替代它
    blocker_type:        # 可选；CR/QA 的 blocked 且精确为 bug 时显示虫子；CR 的 test_assets 标记独立测试资产阻断
    metrics:             # 服务端自动填充该角色 elapsed_ms；首次可提供实测基线
    summary:
    evidence: []
    risks: []
    next_action:
    subskills: []        # 可选；所属角色实际调用的子技能记录，格式见下文

```

角色间箭头中部按当前任务的明确 `handoffs[].files` 逐行展示紧凑文件名标签，悬停显示完整路径。仅取 `work_unit_id` 明确匹配且连接当前相邻角色对的最近交接：须按展示顺序正向、`handoff_result=accepted` 且有合法文件数组；最新记录未接受、逆向或没有文件时不回退旧记录。路径复用文件条校验并按完整值去重，不解析摘要、证据或当前操作文件；无有效文件保持原箭头。标签限制在角色栏内、长名省略、辅助技术可读，不改变状态、箭头居中或既有动效。

交接动效只消费权威 `handoffs`：编排者为每次新建的角色交接填写当前任务的 `work_unit_id`，并生成非空、在同一工作单元内唯一且稳定的字符串 `handoff_id`，`from`、`to` 使用小写角色名。同一次交接由 `pending` 转为 `accepted` 时保留 ID；返工或重新交接使用新 ID，不因刷新生成新 ID。此字段是兼容扩展，旧记录没有 ID 仍正常展示状态，不生成动画。

同一根元素、同一 `view_id` 在已观测历史后，仅末尾新增一条 `accepted` 交接，或末尾同一条 `pending` 转为 `accepted`，才可能播放；先前记录的身份和接收结果须保持不变。接收角色必须在该快照中显式 `status=running`，双方必须是当前选中链中相邻角色；若记录提供 `work_unit_id`，还须匹配当前任务。正向沿线向下，逆向返工时流光和箭头短暂向上；跨多角色或批量补入历史保持静态，避免把中间角色误画为交接参与方。卡片提亮不改变状态、手动展开或焦点，结束后继续既有活动呼吸。

首次装载、不同根元素初次展示、切换任务后返回、相同快照刷新及历史改写均不重播；曾观测的 `accepted` ID 会去重。暂停、等待、阻断、结束、接收角色未明确运行或 `prefers-reduced-motion` 下不播放，该条记录仍视为已观测，之后恢复运行不会补播。根元素销毁或重新挂载后重新建立静态基线，不保存磁盘记录、不轮询、不补放历史。减少动态偏好禁用全部动画和过渡，仍完整展示状态。

角色精确 status=pending 时，角色名和“待开始”仅在左侧角色卡展示，右侧详情正文留空，不保留标题栏或分割线；即使快照包含摘要、证据、风险、下一步或子技能，也不渲染内容、占位或可聚焦控件。窄屏内联详情遵循同一规则，其余角色状态按既有详情展示，不改写快照状态。桌面右侧任务信息框保持右边缘对齐上下文，在原列宽 90% 基础上向左扩展 27px，横向归属线相应缩短 27px；窄屏完成总结仍为 100% 宽。角色正文按摘要、必要证据、风险的顺序纵向单列展示，三个标题由 11px 增至 13px，正文及任务总结字号不变；正文增加留白与分区间距，在可用高度内顶部对齐，各块文字左对齐，长内容自然撑开且不新增滚动区。窄屏同源正文单列；可见正文与自然尺寸保留副本复用相同布局和间距，悬停切换不改变面板尺寸，任务总结布局不变。角色详情在桌面与窄屏均不展示“下一步”字段或空白标题；权威 `next_action` 与交接信息保持原有契约，任务总结同样不展示“下一步”。

角色卡在桌面与窄屏均采用左右两列：左侧角色名，右侧当前状态，两列用竖线分隔。右栏状态和后续内容左上对齐，角色名保持居中。右栏状态下方为仅在 `passed` 时展示的耗时，再下方先按既有规则过滤当前任务权威 `subskills` 数组，再按有效名称首次出现顺序展示所有不同子技能，每个名称一行，同名调用仅合并派生展示，角色框随内容自然增高；无有效数据时保留一行留白，没有耗时时名称直接位于状态下方。合法活动角色仅让最后一项有效且精确 status=running 记录对应的名称播放流光，其余名称保持默认 muted 静态显示；`pending` 不展示子技能。名称沿用既有合法名称、所属角色及真实非空内容校验，不根据角色状态生成记录，非法活动快照或任务停止时不暗示名称正在执行。仅合法活动角色所选的有效、精确 status=running 子技能名称与角色“进行中”同步流光；同名合并不影响运行记录判定，不因首条同名记录已结束而漏掉后续有效 running。每条名称单行省略，悬停显示完整文本，右侧详情及窄屏内联正文均不生成子技能标题、列表、折叠控件或占位；耗时与状态仍可在列内换行，横向归属线和竖向流转箭头仍保持卡片居中。

角色名称标记固定为：REQ 为 Hange、DEV 为 Eren、CR 为 Armin、QA 为 Mikasa。名称仅用于角色标记，不在任务视图中展示，不代表 subagent 名称或身份，不参与状态、交接、权限或完成门禁。视图标题仅显示 REQ、DEV、CR、QA。

编排者每次构建快照时，按当前任务填写 `task_type`、实际参与的 `roles` 和 `role_selection_reason`；顶部不展示项目名、视图 ID 或 subagent 名称。MCP server 为包含 object `work_unit` 的快照自动填充 `work_unit.metrics.elapsed_ms` 和选中角色的 `role_details.<role>.metrics.elapsed_ms`，使用当前服务会话的单调时钟。任务耗时累计各角色活动时段的并集，不能把并行角色数字相加作为任务总量；角色耗时分别累计。计时只认所选角色自身 `status=running`，也不根据 `dev_in_progress` 等任务总状态推断角色运行；显式等待用户、暂停、等待、全局 blocked、测试通过、完成、失败或取消状态会停止全部计时；cr_blocked、qa_failed、qa_conditional 下若有显式 `running` 角色，仍累计返修耗时，无 `running` 角色则不累计，其他未知状态不自行推断活动角色。首次观测的任务或角色可以用非负安全整数 `elapsed_ms` 作实测基线，未提供时从 0 开始；服务入口按 Schema 拒绝非法指标值；后续回传值不覆盖服务端累计值，避免重复累计。Token 用量不再采集或展示；旧 `total_tokens` 字段仅兼容透传。视图不得自行计时、推算或求和。`project_mcps` 只填写已在当前项目生效的 MCP 名称（例如 `codegraph`）：必须同时具备当前项目已初始化的证据和当前会话工具可用性，缺任一项都不填写；不填写地址、参数、密钥或未经确认的候选项。名称会转为小写，且仅接受字母开头、由字母、数字、`.`、`_`、`-` 组成的 1–64 字符标识。有效值在左上角以默认折叠的“项目 MCP”展示，无值时完全隐藏，视图不得读取或推断本机宿主配置。参与角色只展示 `work_unit.roles` 中规范化、去重后的 req/dev/cr/qa，未提供有效角色时显示“尚未选择”，不根据状态猜测参与链。任务上下文中的 `scope`、`acceptance`、`environment` 保留在权威快照中但不在 UI 展示。主流程仍止于 QA 卡，任务总结只读组织现有字段，最多展示三组：`summary` 为“结果”短段落、`verified_scope` 为“已验证”列表、`unverified_scope` 与 `risks` 为“注意事项”列表（分别保留“未验证：”“风险：”前缀）。`summary` 只接受字符串；三个列表字段只接受字符串数组；任务总结不消费 `next_action`，该字段仍保留在权威快照及工作流中。字符串去首尾空白，非法类型和空白项不展示，无内容分组不占位，字段缺省不推断为通过或无风险；全部为空时正文留白，保留任务总结标题和容器；不从角色摘要推造结果。完成快照由编排者填写真实 `work_unit.summary` 与验证范围，兼容旧快照缺失字段；用户明确填写的字面“暂无总结”仍按有效内容保留。旧 `summary` 单字符串保持可读，不解析 Markdown 或自动改写；详情与总结分组复用现有 section，以轻量独立边框包住标题和段落/列表，纵向排列，不增加包装、折叠或动画。总结不是额外角色或完成门禁。任务达到既有耗时结束态（成功完成、测试通过、失败、取消或跳过）且所有选中角色均无精确 `status=running` 时，桌面右侧默认展示“任务总结”；悬停或聚焦角色仍可查看原详情，离开后恢复总结。进行中、暂停、等待、阻断、待用户确认及终态残留 running 时不展示任务总结，视图不再保留底部独立总结框。窄屏仅在结束态显示同一个详情区域中的总结，角色详情仍在原卡片中内联展开，悬停或聚焦角色不替换窄屏总结。总结与角色详情共用自然尺寸保留区，切换不压缩展开空间；文本一律经 textContent 输出。横向归属线保留移动亮条，不显示箭头尖，竖向流转箭头不变；角色边框呼吸、横线亮条和进行中文字流光共用 1.8 秒 CSS 周期，缓动和相位不强制同步，减少动态偏好仍禁用全部动画。

耗时在角色启动、状态变化与空参数恢复视图时结算，不使用页面定时器或轮询；必须及时发送暂停和结束快照，服务端无法知道未上报的状态变化。相同 `view_id` 在当前服务会话中恢复不会重置，最多保留 128 个计时记录；达到上限后明确拒绝新任务，不静默淘汰旧记录。记录只存内存，服务重启后不能恢复未保存的历史时段，只能从重新提供的实测基线或 0 开始。无 object `work_unit` 的纯视图快照保持原样，不生成新计时记录；但同一 `view_id` 的显式停止状态仍会结算并暂停已有计时，纯快照不启动或恢复计时。

任务视图将当前 `snapshot.state` 和角色 `status` 映射为中文标签，不显示英文状态值；REQ、DEV、CR、QA 的角色状态仅为 `pending`（待开始）、`running`（进行中）、`passed`（通过）、`blocked`（阻断）、`needs_user_confirm`（待用户确认）。写入仅接受这五个精确小写值，拒绝别名、大小写变体和非字符串；直接渲染的旧快照未知值显示“未知状态”，缺失角色状态显示“状态未提供”，不由任务阶段推断角色运行，权威快照值不变。任务累计耗时仅在任务结束后展示在任务元数据中，角色耗时在桌面和窄屏均仅显示于左侧角色卡状态下方，以“耗时 2秒”展示，长耗时自然换行；右侧详情不再保留角色、状态或耗时标题栏及其分割线，也不预留标题空白，角色详情正文和窄屏内联正文不重复耗时。总结标题“任务总结”位于总结内容内，无标题栏或分割线。角色耗时仅在对应角色 `passed` 后展示；角色其余四种状态隐藏角色耗时，返修回到 `running` 时重新隐藏；任务进行中、暂停、等待和阻断时隐藏任务耗时；毫秒值格式化为天、小时、分、秒，直接渲染旧快照时非法或缺失耗时值留白。卡片使用克制圆角和短过渡；尊重 `prefers-reduced-motion`。不展示状态机、状态参考集、复验入口或 `resume_state`。`resume_state` 仍是 `state=needs_revalidation` 时的必填权威工作流字段，只是不进入该极简 UI。全部外部展示值须经 DOM `textContent` 输出；模板不得联网、引入第三方依赖、保存远端数据、执行状态变更或嵌入示例定时轮播。

左侧角色卡中的“进行中”仅在所属角色等于视图解析出的合法活动角色时播放持续文字流光；该角色须为唯一且精确 `status=running`，并满足任务未停止、参与顺序及 QA 的 CR 前置条件（含独立测试资产限定返修）。任务停止、活动角色无效、切换到其他状态或无角色时立即停止，原始状态文字与数据保持不变。角色状态与其下方合法运行子技能名称复用同一 `sc-status-shimmer` CSS 规则，周期 1.8 秒、linear、infinite，同时挂载从相同相位开始，悬停或焦点切换不重启其中一项；历史、已结束、未知、空白或 pending 子技能名称不播放。子技能名称保留默认 `var(--muted)` 基色，运行流光使用中性色亮部，状态原青蓝渐变不变；两者仍共用同一动画时序。使用 CSS，不新增计时器或依赖，不改变布局；减少动态偏好或不支持文字裁切时保留静态可读文字。

子技能状态独立于五种角色状态，沿用各子技能的实际契约（如 `waiting_user`、`needs_revision`、`running`、`completed`），不把子技能状态上报为角色状态。`role_details.<role>.subskills` 是可选数组，每项包含 `name`、`status` 及可选字符串 `goal`、`summary`、`question`、`result`，`options` 和 `evidence` 只接收字符串数组。只记录该角色实际调用的子技能：REQ 支持 `align-with-visuals`、`grill-with-docs`；DEV 支持 `tech-select`、`refactor-with-goal`、`bug-fix`、`bug-cause`、`optimize`；CR 支持 `review-with-goal`；QA 支持 `test-with-goal`。非法名称、角色不匹配、错误类型和空白内容不展示；只有名称或状态、没有任务内容的项也不展示。问题与候选选项保留在权威快照中，不进入任务信息正文。

子技能仅在左侧角色卡逐行展示去重后的有效调用名称与合法运行流光，不在任务信息正文中展开内容。编排者保留本轮实际调用记录，更新某项状态时不覆盖其他已调用项。展示使用当前任务权威数组，只合并派生展示，权威调用历史保持原样，不缓存或补造历史，不修改 `subskills`、服务端契约或交接信息；视图不回传选择、不启动技能、不执行审批或改变权威状态。

`view_id` 不是文件名、路径或资源 URI。编排者对同一工作单元始终使用 `sc-task-view:<work_unit_id>`；MCP server 仅校验它是非空字符串，UI 不展示、不解析，也不用于定位本地产物。

## 何时启动

- 用户未明确启动 `sc` 时，任务需要两个及以上角色、明确交接、公共契约评估或风险升级才启动。
- 用户未明确启动 `sc` 且任务只需单个角色时，直接使用对应 Skill，不启动调查兵团。
- 先读取用户任务和必要的仓库上下文，再选择最小角色链。只有目标、权限、环境或风险会改变决策时才询问用户。

## 串行角色与交接

同一工作单元按所选场景链路串行推进，同时最多一个角色处于 `running`。角色切换时，先结束当前角色的执行并记录真实结论，在同一快照中更新前一角色，再把接收角色设为 `running`；不得保留上一轮 running。CR 未通过时 QA 保持 `pending`，仅下述独立测试资产限定返修可启动；不得提前进行常规测试准备、异常复现或正式测试。优化可由 CR 先建项；未登记异常先由 DEV 调查，交 CR 通过后才进入 QA。

QA 在 CR 通过后准备或修改独立测试资产，完成后先停止 QA，再将变化后的基线交 CR 复审，通过后才启动 QA 正式测试。CR 因独立测试资产阻断时，编排者保留任务 `state=cr_blocked`、CR 的 `status=blocked` 与 `blocker_type=test_assets`；由 CR 在最新一条交接中限定修复文件、原因和解除条件，QA 接收后仅修复指定资产，不执行正式测试或输出验收结论。交接须为 `from=cr`、`to=qa`、`state=cr_blocked`、`handoff_result=accepted`，且 `work_unit_id`、`reference_version` 为与当前任务相同的非空字符串，`files` 为非空路径字符串数组，每项须通过文件条的本地路径校验（拒绝 URL、控制字符、UNC 和 `..` 路径段），`decision`、`next_action` 为非空字符串；不以用户临时例外代替此规则。优化链的前序 CR 阻断后交 DEV 返修也复用同样字段，`to=dev`。QA 交 DEV 返修复用上述交接字段，`from=qa`、`to=dev`、交接 `state=qa_failed` 或 `qa_conditional`，所选 QA 保持 `blocked`；任务为对应状态，或 `needs_revalidation` 且 `resume_state=dev_in_progress`。此时旧 CR 结论可置为 `pending` 或保留实际 `blocked`，不保留失效的 `passed`；其他显式未完成前序角色仍须先完成，不新增角色状态。修复完成先停止返修角色、更新基线并将任务置为 `ready_for_cr`，CR 重新运行并通过后才进入 QA 正式测试；旧限定交接不授权新基线。返修也遵循单角色执行，再依次复审、复测。

角色通常按 `pending -> running -> passed` 推进，`passed` 表示工作完成并满足要求；无法推进时转为 `blocked`，用 `summary` 说明原因、`next_action` 说明解除条件，解除后 `blocked -> running` 返修。需用户决定时转为 `needs_user_confirm`，未获确认不得继续；用户回复后按实际条件回到 `pending`、`running` 或 `blocked`。暂停、取消属于任务状态，不增加角色状态；未参与角色不列入角色链。任务 `state` 表示阶段或整体结果，角色 `status` 表示执行状况，`handoff_result` 表示交接接收结果，三者不能互相替代。

准备工作在所属角色获得执行权后进行；等待上游结论不算执行，不得以摘要说明“等待”却继续上报 running。本规则不修改耗时计算。

## Subagent-only 执行约束

调查兵团一旦被调用，所选择的每个角色都必须作为独立的真实 subagent 执行。调查兵团可以由当前代理负责编排、收集交接和汇总结果，但不得由当前会话直接代办角色工作，也不得用普通新会话、独立任务或文字模拟角色来替代 subagent。

- 角色启动必须使用当前执行环境提供的真实 subagent/协作代理机制，不绑定特定宿主、客户端或具体工具名称；只要目标环境具备等价的 subagent 能力即可启动。普通新会话、独立任务或其他创建会话的机制不算角色 subagent，除非平台明确将其标记为当前任务的 subagent。
- 角色之间按本技能的交接协议传递工作单元和证据；子技能在所属角色的 subagent 内执行，不另行创建普通新会话。
- subagent 能力不可用、启动失败、角色无法独立接收任务或交接证据无法回收时，立即将调查兵团标记为 `blocked`，说明阻断原因和恢复条件。
- 禁止降级为当前代理内联执行、顺序模拟角色、仅输出角色口吻，或为了继续推进而自动创建普通新会话。

## 最小编排

只读取和启动已选择角色的本体 Skill。调查兵团的任何场景只要其范围包含代码改动，该场景的完整链路就必须包含 `cr` 和 `qa`，并在最终代码基线上完成审查与测试；无代码改动的场景不因此强制增加这两个角色。下表给出各个场景的工作流链路，完成前统一执行下文的完成门禁。每个活跃角色仍按自身本体 Skill 的条件选择专属从属 Skill。

| 情形 | 场景链路 | 需要时使用的从属 Skill |
| --- | --- | --- |
| 需求或影响不明 | `req`；需求收敛后按当前场景选择后续链路 | 有文档且存在高风险歧义：`grill-with-docs`；视觉化能消除歧义：`align-with-visuals` |
| 已确认的功能或行为变更 | `dev -> cr -> qa` | 无 |
| 受控重构 | `dev -> cr -> qa` | `refactor-with-goal`、`test-with-goal` |
| 未登记异常 | `dev（调查） -> cr -> qa` | `test-with-goal` |
| 已登记缺陷 | `dev -> cr -> qa` | `bug-fix`、`test-with-goal` |
| 性能、容量、成本或资源效率优化 | `cr（建项） -> dev -> cr（复审） -> qa` | `optimize` |

需求或影响不明且歧义会改变方案或验收时先由 `req` 收敛，再选择主场景；用户提出请求本身不构成启动 REQ 的理由。代码变更同时符合多行时，按缺陷修复、量化优化、受控重构、功能变更选择主链路；混合目标拆分工作单元并保留各自门禁。未登记异常由 `dev` 调查并按已确认范围修正，CR 通过后由 `qa` 核验反馈证据、复现和登记；已登记缺陷从 `dev` 开始。优化先由 `cr` 建项，实施后复审。

高风险包括公共 API、权限、数据库或迁移、金额/事务和不可逆操作，是所有主场景的叠加门槛：需求或验收未确认时前置 `req`，实施前确认方案协议，不因风险等级替换缺陷、优化等主链路。代码同步、发布预检、生产发布及运行观察不属于调查兵团流程，由用户或授权方负责；这些操作改变代码基线时，调查兵团须按新基线重新完成 `cr -> qa`。

## 共同约束

每个活跃角色先定义并更新最小工作单元：

```yaml
work_unit:
  work_unit_id:
  target:              # 要交付的结果
  roles: []            # 本轮实际角色
  reference_version:   # 需求、代码、配置或依赖的当前基线
  environment:
  verified_scope: []
  unverified_scope: []
  acceptance: []
  risks: []
  evidence: []         # 路径/行号、命令和结果、测试或事件 ID；不猜测 URL
  next_action:
```

- 结论按“观察 → 解释 → 边界 → 行动”表达；不能将局部、旧版本或其他环境的证据扩大为系统结论。
- 需求、代码、配置、依赖、数据或环境变化时，只要影响旧结论，就让受影响的下游结论重新验证；不复用失效证据。
- 工作单元只记录会影响执行或结论的字段；时间敏感证据补充观察时间与有效期，高风险任务按下一节补充门禁。不为模板完整度创建额外文档或空字段。

新模块、公共 API、数据库、权限、事务、缓存/MQ 或不兼容变化实施前，建立最小方案协议：`protocol_id`、版本、范围、契约/数据/安全影响、恢复路径、裁决者和 `draft | needs_user_confirm | confirmed | invalidated` 状态；未到 `confirmed` 不实施高风险变更。

## 图示对齐

当组件、流程、依赖、状态或影响范围的关系会影响当前决策时，可用图示辅助对齐：静态关系图优先 Mermaid，无法渲染时输出等价的 ASCII 字符图；只有需要交互探索或用户明确要求时才使用 HTML。图示中的事实、假设和开放问题必须显式区分，不替代契约、测试、审批或交接记录。

## 高风险门槛

高风险任务必须对以下受影响项给出当前基线和可核验证据；未触及的项只写一行影响判断，不伪造“通过”。

| 项目 | 最低证据 |
| --- | --- |
| 功能与契约 | 已确认验收，以及 API/业务行为影响 |
| 质量与测试 | `dev` 的构建/静态检查/实现单元测试，以及 `qa` 的独立主路径、边界和受影响回归 |
| 安全与数据 | 权限/输入输出边界、数据不变量、迁移或补偿 |

`P0` 是已发生或迫近的生产中断、重大安全事件或数据损坏；`P1` 是已发生或迫近的关键契约、权限或核心流程失效。确认 P0/P1 后冻结受影响动作并记录 `event_id`、影响、责任人、证据和恢复条件；修复后从最早失效环节重新验证。

## 交接与状态

场景链路由上表确定；只运行当前场景选择的角色。每次交接使用：

开发场景状态为 `confirmed -> planned -> dev_in_progress -> ready_for_cr -> ready_for_qa -> qa_passed -> workflow_ready`；优化先由 `planned -> ready_for_cr` 建项，再进入 `dev_in_progress`，实施后复用 `ready_for_cr` 复审。QA 通过后由编排者核验门禁并将状态记为 `workflow_ready`。高风险事项尚待裁决时前置 `needs_user_confirm`；CR 阻断走 `cr_blocked -> ready_for_cr`，`qa_failed` 或 `qa_conditional` 按下文返修闭环处理，不能进入工作流完成。全局 `blocked` 的合法来源包括已确认的 P0/P1、未授权执行、任务视图 MCP 前置不可用，以及 subagent 能力不可用或交接证据无法回收。

需求、实现、配置、依赖、迁移、契约、权限、安全、数据、测试证据或环境变化时进入 `needs_revalidation`，按最早失效环节计算 `resume_state`；仅同一基线下补材料使用 `needs_revision`，不改变工作流状态。

```yaml
handoff:
  work_unit_id:
  handoff_id:          # 可选；同一任务内唯一且稳定；任务视图仅用它去重真实交接动效
  from:
  to:
  state:
  handoff_result: pending | accepted | needs_revision | rejected
  reference_version:
  files: []           # 可选；明确交接的文件路径字符串数组，不从摘要、证据或操作文件推断
  verified_scope: []
  unverified_scope: []
  evidence: []
  decision:
  risks: []
  next_action:
```

- 角色切换时由独立 subagent 记录交接；同一角色连续执行子技能可复用工作单元，不新增角色交接。接收方填写 `handoff_result`；`needs_revision` 表示同一基线下材料不全，`rejected` 表示职责、授权或结论不可接受，并在 `decision` 中说明原因；基线失效进入 `needs_revalidation`，确认 P0/P1 进入 `blocked`。
- 问题按所属资产派发：业务实现、配置、契约及实现单元测试归 `dev`；独立测试资产及其配置、fixture、测试预言机归 `qa`，测试环境或测试数据问题由 `qa` 处理或协调。未解决的一般阻断项保持其来源状态（如 `cr_blocked` 或 `qa_failed`）；已确认 P0/P1、未授权执行、任务视图 MCP 前置不可用或 subagent 前置不可用时进入全局 `blocked`。
- 角色边界：`req` 负责需求和验收标准；`dev` 负责实现、实现耦合的单元测试及恢复输入；`cr` 负责静态审查发现和复审；`qa` 负责独立正式测试、Bug 生命周期和验收结论；用户或授权方负责代码同步、发布与运行操作。

## 完成门禁与返修闭环

编排者负责核验完成门禁。只有以下条件全部满足，才能宣布“工作流完成”“任务完成”或同义结论：

- 本场景范围包含代码改动时，`cr` 和 `qa` 均须由独立真实 subagent 执行并回收结论；CR 明确通过，QA 的 `conclusion=pass` 且交接状态为 `qa_passed`。未运行、未返回、条件通过、证据不足或用户接受风险均不能替代通过。无代码改动时，按该场景链路完成所有选定角色及其适用门禁。
- 本场景范围包含代码改动时，`cr` 与 `qa` 的结论必须绑定同一最终 `work_unit_id`、`reference_version`、范围及适用环境，证据仍有效；最后一次相关修改后的受影响审查和测试已重新执行。
- 当前范围内未关闭的 CR 阻断项、高风险项、QA 阻断 Bug 及其他角色阻断项均为零，验收退出标准全部满足。
- 已选角色的工作与交接已完成；用户尚未同步代码或发布不影响调查兵团代码工作流完成。同步、发布或运行观察不属于本工作流的完成门禁。

CR 未通过时，实现及单元测试问题交 `dev` 处理，再回到 `ready_for_cr` 复审；独立测试资产问题按上述限定交接由 QA 返修，再回到 `ready_for_cr` 复审；QA 正式测试仍须等待 CR 通过。QA 未通过时按资产归属处理；代码（含测试代码）、配置或契约改变后走 `ready_for_cr -> ready_for_qa`，复测原失败及受影响回归；仅恢复测试环境或数据且 CR 证据仍有效时可直接回到 `ready_for_qa`。同一有效基线上 QA 通过后由编排者核验完成门禁并记为 `workflow_ready`。用户同步产生新代码基线时重新经过 `cr -> qa`，其他证据失效按最早失效环节恢复，禁止沿用失效的通过结论。

在已有授权和任务范围内持续推进上述闭环，不把“角色已执行一轮”“报告已生成”或“已列出待修问题”当作完成。无法继续时（例如缺少权限、环境、依赖或关键决策，或连续两轮修复后同一阻断仍无实质进展），停止重复尝试，保留实际阻断或待处理状态，报告阻断证据、已尝试动作和恢复条件；只能声明“工作流未完成”，不得宣布成功。用户暂停或取消也不算通过。

本场景范围包含代码改动时，最终完成报告必须列出最终基线、CR 通过证据、QA 通过证据以及未关闭阻断项数量（必须为 0）；无代码改动时列出实际选定角色的完成证据和未关闭阻断项数量。非阻断建议可保留并说明范围，不扩大为无风险保证。

## 外部操作边界

用户或授权方负责代码同步、发布预检、生产发布及部署后运行观察。调查兵团不执行这些操作，也不把它们列为工作流完成门禁；若操作改变已审查或测试的代码基线，须从最早失效环节重新验证。
