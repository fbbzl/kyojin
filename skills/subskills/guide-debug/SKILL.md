# guide-debug

当定位问题依赖 Codex 无法直接访问的环境、系统或数据时，由 `dev` 或 `qa` 带用户逐步采集证据。每轮提出具体检查动作，等待用户执行并回传结果，再据此选择下一步；不把猜测写成根因。

## 适用边界

- `dev` 可用于用户报告或开发中发现的问题调查，也可用于 `bug-fix` / `bug-cause` 中需要外部证据的诊断；`qa` 可用于 CR 通过后收集环境侧复现与测试证据。它不改变既有角色链、CR 前置条件或职责归属。
- 可先检查当前仓库和已有文档，整理功能的预期业务生命周期；仅把无法从当前会话安全取得的部分交给用户操作，不要求用户代做 Codex 能完成的检查。用户确认生命周期前，不开始按故障假设检查外部环境中的实际数据。
- 它只负责排查和证据交接，不实现修复、不代替 `cr` 审查、不登记或关闭 Bug，也不输出 QA 验收结论。

## 逐步排查

1. 确认现象、影响范围、发生时间、最近一次正常时间及关联版本/环境。只询问会改变排查路径的信息。
2. 先和用户梳理功能的预期业务生命周期：起始事件、参与方、状态及转换条件、分支、数据写入和外部副作用、重试/补偿路径、成功或失败的终态。预期以既有契约或已确认需求为准；依据缺失或与用户描述冲突时，先交需求责任方澄清，未明确前不开始故障追踪。可用仓库和文档起草，但要区分已知事实与待确认项。
3. 把生命周期按发生顺序呈现给用户，请其确认完整且符合预期，尤其确认本次问题涉及的分支和终态。若用户指出遗漏或流程本身不符合预期，先修正生命周期；未获确认前不进入故障追踪。
4. 生命周期确认后，选取一个受影响的具体业务过程或业务记录，并确认至少一个能贯穿全流程的业务关联值（如订单号、申请单号、交易号或请求关联 ID），以及它如何对应各阶段的记录。用同一个关联值从生命周期起点沿顺序追踪，逐阶段记录预期状态/事件与实际观察、时间及证据来源；标出第一个不一致或证据缺口。若没有稳定的关联值或关联规则，先把它作为追踪阻断点，向用户索取最小补充信息，不拼接无法确认属于同一过程的记录。
5. 每轮只选一项能验证当前链路的低风险检查，优先核对相邻阶段的输入、输出和状态变化。根据结果顺藤追踪：首个偏差出现前检查其上游触发和条件，出现后检查其直接原因及下游影响；有证据再扩展，不做无关层面的散点排查。
6. 指明用户在哪里、以何种权限和环境执行；给出可直接使用的命令或 SQL、需要替换的占位符、预期观察项，以及如何脱敏和回传。SQL 方言或工具版本不明确时先确认，不猜表、字段、地址或凭据。
7. 等待用户回传实际输出。说明它能支持或排除什么、生命周期追踪到哪一阶段、仍有哪些不确定性，再选下一项检查；若结果与假设不符，更新链路判断，不重复同一无效步骤。
8. 证据足以定位时，交付已确认原因及证据链、首个偏差阶段、影响边界、仍未验证内容和下一责任侧。证据不足时说明当前最可能解释仍是假设，并给出能继续区分它们的具体观测或阻断条件。

连续两个追踪点都未增加有效证据时，暂停新增检查，重新核对已确认的生命周期、实例标识和链路假设；仍无法推进则停止并向用户说明阻断及所需的最小补充证据，不循环试错。

## 用户执行与安全

- 在生产或共享环境中默认只请求只读查询。SQL 优先使用范围明确、限制行数的 `SELECT` 或元数据查询；Kafka、Redis、系统和云平台检查优先使用查看状态、配置摘要、积压/键数量等只读命令。
- 不让用户在诊断步骤中执行 `UPDATE`、`DELETE`、`INSERT`、`FLUSH*`、清理、重启、扩缩容、权限变更、数据回填或其他有副作用的动作。若进一步验证确实需要写入或改变运行状态，先说明影响、恢复方式和判定目标，暂停该动作并走现有授权/方案确认流程。
- 不要求用户粘贴密码、Token、连接串、私钥或完整敏感数据。提示遮盖个人信息和业务数据；只索取判定所需的列、样例或统计结果。
- 步骤须与已确认的系统、环境和权限匹配。涉及高风险服务、生产数据或可能扩大故障的操作时，先确认目标环境和操作授权；无法确认则停止该步骤。
- 用户无法执行、结果缺失或权限不足时，记录实际限制和需要的最小证据；不以空结果当作系统正常，也不编造可运行语句或执行结果。

## 输出

先记录经用户确认的预期生命周期和贯穿流程的业务关联值（必要时脱敏）；追踪时记录目标环境/服务、版本或配置基线、各阶段的预期与实际、观察时间、脱敏后的命令或 SQL、结果摘要及其对因果链的影响，并标明首个偏差、已验证/未验证范围和下一步。敏感输出先脱敏再引用。排查结束时区分已确认根因、可能原因和无法判断的部分，并按现有职责交给 `dev` 修复、`cr` 审查或 `qa` 继续复现/验收。
