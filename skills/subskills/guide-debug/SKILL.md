# guide-debug

当定位问题依赖 Codex 无法直接访问的环境、系统或数据时，由 `dev` 或 `qa` 带用户逐步采集证据。每轮提出具体检查动作，等待用户执行并回传结果，再据此选择下一步；不把猜测写成根因。

## 适用边界

- `dev` 可用于用户报告或开发中发现的问题调查，也可用于 `bug-fix` / `bug-cause` 中需要外部证据的诊断；`qa` 可用于 CR 通过后收集环境侧复现与测试证据。它不改变既有角色链、CR 前置条件或职责归属。
- 先检查当前仓库、已有日志和可用工具能直接提供的证据。仅把无法从当前会话安全取得的部分交给用户操作，不要求用户代做 Codex 能完成的检查。
- 它只负责排查和证据交接，不实现修复、不代替 `cr` 审查、不登记或关闭 Bug，也不输出 QA 验收结论。

## 逐步排查

1. 确认现象、预期行为、影响范围、发生时间、最近一次正常时间及关联版本/环境。只询问会改变排查路径的信息。
2. 根据现有证据列出少量可区分的假设，覆盖实际相关边界，例如业务代码、数据库结构/数据/编码、配置、权限、消息队列、缓存、网络、运行环境或依赖服务；注明哪些已证实、待证实或已排除。
3. 选择当前最有区分力且风险最低的一项检查。一次给一个清楚的操作单元；只有必须一起完成的同一只读检查才合并请求。
4. 指明用户在哪里、以何种权限和环境执行；给出可直接使用的命令或 SQL、需要替换的占位符、预期观察项，以及如何脱敏和回传。SQL 方言或工具版本不明确时先确认，不猜表、字段、地址或凭据。
5. 等待用户回传实际输出。解释输出能支持或排除什么、仍有哪些不确定性，再提出下一项检查；若结果与假设不符，更新假设，不重复同一无效步骤。
6. 证据足以定位时，交付已确认原因及证据链、影响边界、仍未验证内容和下一责任侧。证据不足时说明当前最可能解释为假设，并给出能继续区分它们的具体观测或阻断条件。

连续两项检查都未缩小故障范围时，暂停新增检查，重新核对基线和假设；仍无法推进则停止并向用户说明阻断及所需的最小补充证据，不循环试错。

## 用户执行与安全

- 在生产或共享环境中默认只请求只读查询。SQL 优先使用范围明确、限制行数的 `SELECT` 或元数据查询；Kafka、Redis、系统和云平台检查优先使用查看状态、配置摘要、积压/键数量等只读命令。
- 不让用户在诊断步骤中执行 `UPDATE`、`DELETE`、`INSERT`、`FLUSH*`、清理、重启、扩缩容、权限变更、数据回填或其他有副作用的动作。若进一步验证确实需要写入或改变运行状态，先说明影响、恢复方式和判定目标，暂停该动作并走现有授权/方案确认流程。
- 不要求用户粘贴密码、Token、连接串、私钥或完整敏感数据。提示遮盖个人信息和业务数据；只索取判定所需的列、样例或统计结果。
- 步骤须与已确认的系统、环境和权限匹配。涉及高风险服务、生产数据或可能扩大故障的操作时，先确认目标环境和操作授权；无法确认则停止该步骤。
- 用户无法执行、结果缺失或权限不足时，记录实际限制和需要的最小证据；不以空结果当作系统正常，也不编造可运行语句或执行结果。

## 输出

每项检查记录目标环境/服务、版本或配置基线、观察时间、脱敏后的命令或 SQL、用户回传的结果摘要及其对假设的影响；同时保留已验证/未验证范围和下一步。敏感输出先脱敏再引用。排查结束时区分已确认根因、可能原因和无法判断的部分，并按现有职责交给 `dev` 修复、`cr` 审查或 `qa` 继续复现/验收。
